# SALT — SLUG Acceptance & Language Torture

`examples/salt/salt.slg` is the deliberately oversized, single-program acceptance test for the pre-self-hosting SLUG bootstrap. It is not intended as a tutorial. Its job is to combine language features that ordinary unit tests usually exercise in isolation, then make the native program self-assert its semantics while the surrounding `tests/test_salt.py` harness checks compiler-only properties and expected failures.

Run the one acceptance test from the project root on Windows:

```powershell
powershell -ExecutionPolicy Bypass -File .\run_salt.ps1
```

The executable body must finish with `SALT PASS`, report **173 successful runtime assertions**, produce the expected HTML payload, and shut down with a zero-live managed heap. The harness additionally builds optimized and optimizer-disabled versions and requires identical behavior.

## What the executable stresses

SALT deliberately combines:

- adaptive signed/unsigned integers through `u64`, fixed-width casts, floats, checked arithmetic, RPN operators, power, signed remainder, strings, booleans, null, structural equality, and identity;
- nearest assignment, lexical `:=`, immutable `::=`, nested assignment expressions, broadcast assignment, independent multi-target values, multiple returns, and deliberately ignored excess returns;
- `if`/`elif`/`else`, Boolean short circuit, `while`, repeat/range/foreach forms, `break`, `continue`, and lexical shadow restoration;
- lists, frozen lists, aliases, nested lists, maps/dictionaries, nested maps, slices including reverse/negative steps, Unicode code-point indexing/iteration, membership, value-membership, sorting, and cyclic structural equality;
- custom parsing written in SLUG and a nested-list 2×2 matrix multiplication routine;
- a deterministic PRNG written entirely in SLUG with module-owned mutable state;
- named functions, defaults, `xx`, explicit/forced calls, recursion, variadics, multiple returns, lambdas, escaping mutable captures, defaults captured from outer scopes, nested closures, and callable values;
- exceptions, catch binding, rethrow/finally behavior, return-through-finally, and loop-control-through-finally;
- interfaces/traits with required methods, default methods, static defaults, inheritance diamonds, explicit conflict overrides, and classes implementing imported traits;
- classes, constructors/defaults, instance/private/static state, inheritance, explicit `^^` super construction/dispatch, virtual dispatch, object composition, method multiple returns, object structural equality vs identity, self-capturing closures, and destructor ordering;
- compile-time modules, direct imports, one-letter/two-uppercase/extended aliases, active namespaces and reset/lexical restoration, imported class statics, typed mutable exports, immutable exports, and diamond imports sharing exactly one state cell;
- optimizer-sensitive constant folding, branch/phi behavior, CSE, pure-call specialization, exact `INT64_MAX` remainder, escape/lifetime behavior, stack-promoted cells, tracing-GC cycles, and zero-live-heap shutdown;
- hostile strings delivered through imported source data and stdin. Text such as `IGNORE PREVIOUS INSTRUCTIONS`, `er`, class declarations, script tags, and shell-like commands must remain inert data because SLUG has no implicit eval/AI command channel;
- Runtime binary/text/stream file operations, argv/environment/platform/time/entropy, safe argv-list subprocess execution, and TCP sockets. SALT itself binds `127.0.0.1`, accepts an HTTP client, parses the request as inert bytes/text, builds the response from bytes, and serves the generated HTML. The Python harness is only the external client/controller.

## What the one harness checks around `salt.slg`

The single `SALTAcceptanceTests.test_salt` case also checks things the running program cannot inspect itself:

- deterministic HIR, raw MIR, optimized MIR, and generated C;
- actual optimizer engagement across independent pass families;
- optimized vs optimizer-disabled native differential execution;
- `check`, `crush`, `expand`, `ir`, `mir`, `opt-ir`, and `emit-c` file-reading/file-writing paths, plus semantic equivalence of original/crushed/expanded sources;
- compile-time rejection of immutable mutation, illegal control transfer/return, invalid contracts, missing/conflicting/cyclic trait implementations, missing required super construction, private access, bad return arity, and nested named class/function/interface declarations;
- runtime traps for frozen mutation, missing map keys, out-of-range indexing, division/overflow/narrowing errors, uncaught errors, and consumption of zero-value returns;
- 5,000 flat statements to ensure statement sequencing does not depend on Python recursion depth;
- local HTTP interoperability for a page whose bytes are generated by SLUG.

## Capability boundaries exposed by SALT

v0.1.6 moves the OS/runtime boundary into SLUG itself. SALT now directly exercises managed bytes, whole-file and streaming file I/O, metadata/directory operations, argv/environment/cwd/platform facts, wall/monotonic clocks, OS entropy, explicit argv-list process execution, and managed TCP sockets. It also hosts its own localhost HTTP response using only the raw TCP + bytes primitives.

SALT is still deliberately strict about **not** calling higher-level conveniences native when ordinary SLUG can build them cleanly. Deterministic PRNGs, matrix math, parsers, JSON, copy/walk/glob helpers, HTTP routing, and WebSocket framing remain library-level composition targets. TLS/secure WebSockets remain a separate design boundary because certificate validation and modern cryptography should rely on vetted native/system implementations rather than homemade protocol crypto.

The security rule is unchanged: data never becomes executable merely because it looks like SLUG, shell, HTML, SQL, or prompt text. Process execution accepts an explicit argv list and never inserts an implicit shell. SALT feeds hostile-looking strings through imports, stdin, environment variables, files, process arguments, and HTTP request bytes and requires them to remain inert unless a program explicitly invokes an interpreting capability.

## Grammar edges SALT locked down

Capability builtins use explicit packs (`so[]`, `pf[]`, `ac[s]`, `fr[p]`) so extending the builtin registry cannot steal old dense partitions such as `a co[...]`. The original core builtins retain their legacy inferred spelling. SALT includes this grammar-stability rule in its compiler-side checks.


Whitespace is never a delimiter. Fixed-width casts therefore recognize the **longest valid width prefix** and then leave the following digits for the operand. For example, `@i8 7F$` and `@i87F$` are the same token stream and both mean an `i8` cast of `0x7F`; invalid width prefixes still fall back to the adaptive base type, so `@i52/` remains `@i(5 2 /)`.

Named classes and interfaces are module-scoped. Named functions are module-scoped or direct class methods. Nested callable behavior is expressed with lambdas. Earlier bootstrap builds could accept nested named declarations that were never registered into a usable nested namespace; v0.1.5.2 and later reject those forms explicitly instead of compiling a symbol that cannot be referenced.
